## Protocol adapter types and classes

Every protocol adapter has a fixed type code. `AdapterType` must be set to that code in every deployment mode, and in
the uberjar and in-process modes the `AdapterTypes` key is the same code. The module is the name of the adapter's release
bundle (`<module>.tar.gz`), of its `JarFiles` directory (`${SFC_DEPLOYMENT_DIR}/<module>/lib`) and of its IPC launcher
(`<module>/bin/<module>`). How the three modes use these values:
[Configure a component in each mode](./sfc-deployment.md#configure-a-component-in-each-mode).

## Running the JVM protocol adapters as an IPC Service

The adapters have a service wrapper that enables these adapters to be executed as an IPC Service process. For each
adapter, a tar file (`<module>.tar.gz`) is generated by the build process that includes the application script files to
start the service, as well as all required library files. The script files are named after the module, not the adapter
type (`<module>/bin/<module>` and `<module>/bin/<module>.bat`, e.g. `modbus-tcp/bin/modbus-tcp` for `MODBUS-TCP`), and the
libraries are in `<module>/lib/*.jar`. The module and the IPC service class of every adapter are listed in
[Protocol adapter types and classes](#protocol-adapter-types-and-classes).

Start the service before SFC, on the port of its `AdapterServers` entry, e.g. for OPC UA:

**Linux / macOS**

```shell
tar -xzf opcua.tar.gz
opcua/bin/opcua -port 50000
```

**Windows (PowerShell)**

```powershell
New-Item -ItemType Directory -Force C:\sfc | Out-Null
tar -xf opcua.tar.gz -C C:\sfc
java -cp "C:\sfc\opcua\lib\*" com.amazonaws.sfc.opcua.OpcuaProtocolService -port 50000
```

On Windows start adapter services with `java -cp` and the bundle's `lib\*`, not with `bin\<module>.bat`; see
[Platform support](./README.md#platform-support).

Any adapter service can also be started from the uberjar, which contains all of them. From an sfcup install:
`java -cp "$HOME/.sfc/current/lib/*" <IPC service class> -port 50000` (Windows:
`java -cp "$HOME\.sfc\versions\$(Get-Content $HOME\.sfc\current.txt)\lib\*" <IPC service class> -port 50000`).

In the SFC configuration an IPC adapter keeps its `AdapterType` and names its server in `AdapterServer`. The server is
defined under `AdapterServers`, and no `AdapterTypes` entry is needed:

```json
"ProtocolAdapters": {
  "OPC-UA": {
    "AdapterType": "OPCUA",
    "AdapterServer": "OpcuaAdapterServer",
    "OpcuaServers": {
      "OPCUA-SERVER-1": { "Address": "opc.tcp://localhost", "Port": 4840 }
    }
  }
},
"AdapterServers": {
  "OpcuaAdapterServer": { "Address": "localhost", "Port": 50000 }
}
```

A service listens only on the address its host name resolves to, or on that of the interface given with `-interface`,
which is not necessarily `127.0.0.1`. In `Address` use that address, or `localhost`, which SFC also resolves to the
address of the host name. All server settings: [ServerConfiguration](./core/server-configuration.md).

The applications have the following command line parameters in common.

| Parameter     | Description                                                                                                                                                                                                                                                                                                                                                                                                              |
|---------------|--------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| -config       | Name of an SFC configuration file. The service listens on the `Port` of the `AdapterServers` entry that the adapter selected with `-adapter` names in its `AdapterServer`; missing `-cert`, `-key` and `-ca` values are also taken from that entry. The configuration of the adapter itself always comes from the SFC core, which sends an initialization request with it to the service on this port.                  |
| -adapter      | Key of the `ProtocolAdapters` entry this service runs, used with `-config`. Always give it with `-config`: without it the service currently fails to start, even when the file contains only one adapter.                                                                                                                                                                                                              |
| -connection   | Security level used to secure traffic between SFC core and protocol adapter service. PlainText : No encryption (default) ServerSideTLS : Data is encrypted, requires -cert and -key parameters MutualTLS : Data is encrypted, requires -cert, -key and -ca parameters The connection type must match the ConnectionType of the `AdapterServers` entry the SFC core uses to communicate with the protocol adapter service. |
| -cert         | Server certificate file to secure IPC (gRPC) traffic for connection types ServerSideTLS and MutualTLS                                                                                                                                                                                                                                                                                                                    |
| -key          | Server private key file to secure IPC (gRPC) traffic for connection types ServerSideTLS and MutualTLS                                                                                                                                                                                                                                                                                                                    |
| -ca           | CA certificate file to secure IPC (gRPC) traffic for connection type MutualTLS                                                                                                                                                                                                                                                                                                                                           |
| -interface    | Name or display name of the network interface whose IPv4 address the service listens on (e.g., en0). Default: the address the host name resolves to.                                                                                                                                                                                                                                                            |
| -envport      | The name of the environment variable that contains the port number for the service to listen on for requests.                                                                                                                                                                                                                                                                                                            |
| -error        | Set log output level to error level. (Error message only)                                                                                                                                                                                                                                                                                                                                                                |
| -h, -help     | Shows command line parameter help.                                                                                                                                                                                                                                                                                                                                                                                       |
| -info         | Set log output level to info level. (Info, warning and error messages)                                                                                                                                                                                                                                                                                                                                                   |
| -nocolor      | Disable color coded output to console.                                                                                                                                                                                                                                                                                                                                                                                   |
| -port         | port number for the service to listen on for requests.                                                                                                                                                                                                                                                                                                                                                                   |
| -trace        | Set log output level to most detailed trace level (Info, warning, error, and detailed trace messages)                                                                                                                                                                                                                                                                                                                    |
| -warning      | Set log output level to warning level. (Error and warning messages)                                                                                                                                                                                                                                                                                                                                                      |

Give exactly one of `-port`, `-envport` or `-config`: they are mutually exclusive, and a service started with two of them
stops with a command line error. Put `-config` before the other parameters, e.g.
`opcua/bin/opcua -config sfc.json -adapter OPC-UA -info`; a parameter placed in front of `-config` currently hides it.

To protect the IPC traffic between the core and the adapter service with TLS, start the service with
`-connection ServerSideTLS` and `-cert` and `-key`, or with `-connection MutualTLS` and `-cert`, `-key` and `-ca`, and set
the same `ConnectionType` in the core's `AdapterServers` entry. With `-config`, missing `-cert`, `-key` and `-ca` values are
taken from `ServerCertificate`, `ServerPrivateKey` and `CaCertificate` of the adapter's `AdapterServers` entry, but its
`ConnectionType` is not, so always pass `-connection`. See
[Securing Network Traffic between SFC components](./sfc-securing-component-traffic.md).

**Known limitations**

- An adapter service applies a configuration only when the core sends it for the second time. After the core starts, its
  first read from an IPC adapter therefore fails, and data follows when the core retries, about 10 seconds later.
- After a configuration change, a running adapter service may keep its previous configuration; restart the service to
  apply the change.
- An adapter service sends channel values to the core without their own timestamps, and stamps each source with the time
  it sends the values. Timestamps that an adapter reads with the values, such as the OPC UA source timestamp, therefore
  do not reach the core.

[SLMP to S3](../examples/ipc-slmp-s3/README.md) run the adapter and the targets as IPC services; the
[Greengrass IPC lab](../examples/greengrass-ipc/README.md) runs them as Greengrass components. All examples:
[examples catalog](./examples/README.md).


## Running protocol adapters in-process

To run protocol adapters in the same process as the SFC core, they need to be implemented for the same JDK as used for
the core. To make it possible to add new adapters without making changes to the SFC code, there are no links in the core
to the libraries that implement the adapters. In the configuration of an in-process adapter type, the pathnames of the
jar files that contain the classes that implement the adapter need to be explicitly configured. When the SFC core
creates an instance of the adapter, it loads the configured jar files and uses a static factory method to create the
actual instance. 

The jar files are part of the adapter deployment and can be found in the lib directory of the deployment package. To
specify the path to the jar files it is recommended to use a placeholder, instead of hard-coding, the directory where
the adapter, and targets, are deployed and set an environment variable for this directory.

```sh
${<environment variable name>}/<module>/lib
```

e.g., if the deployment tar file of the mqtt adapter is unpacked in `/sfc`, so that the adapter is in `/sfc/mqtt`, the
environment variable is set to "/sfc". In the configuration for the jar pathnames, this variable can be used as a
placeholder in the pathname of the jar file.

**Linux / macOS**

```shell
export SFC_DEPLOYMENT_DIR=/sfc
```

**Windows (PowerShell)**

```powershell
$env:SFC_DEPLOYMENT_DIR = "C:/sfc"
```

In the configuration, the values for the jar files are "${SFC_DEPLOYMENT_DIR}/mqtt/lib".

Example AdapterTypes section, including the mqtt and opcua in-process protocol configuration with environment variable placeholders.
Each adapter is in a subdirectory of the deployment directory, named after its module.

```json
{
  "AdapterTypes": {
    "MQTT": {
      "JarFiles": [
        "${SFC_DEPLOYMENT_DIR}/mqtt/lib"
      ],
      "FactoryClassName": "com.amazonaws.sfc.mqtt.MqttAdapter"
    },
    "OPCUA": {
      "JarFiles": [
        "${SFC_DEPLOYMENT_DIR}/opcua/lib"
      ],
      "FactoryClassName": "com.amazonaws.sfc.opcua.OpcuaAdapter"
    }
  }
}
```

The uberjar already contains every adapter, so when SFC runs from the uberjar the same entries name only the
`FactoryClassName`; see [Configure a component in each mode](./sfc-deployment.md#configure-a-component-in-each-mode).

**Examples:** [Simulator to S3 Tables](../examples/in-process-sim-s3tables/README.md),
[ADS to S3](../examples/in-process-ads-s3/README.md), [Greengrass in-process lab](../examples/greengrass-in-process/README.md).
All examples: [examples catalog](./examples/README.md).
